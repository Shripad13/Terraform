
Q1: What is a Kubernetes Pod, and how does it relate to containers?Answer: A Pod is the smallest deployable unit in Kubernetes. It represents a single instance of a running process. A Pod can hold one or more containers (like a main app container and a sidecar container). All containers inside a single Pod share the same network namespace (IP address and ports) and storage volumes.

Q2: What is a Service Account in Kubernetes, and how does Vault use it?Answer: A Service Account provides an identity for processes running inside a Pod so they can authenticate with the Kubernetes API or external systems. Vault leverages this via the Kubernetes Auth Method: a Pod presents its automatically injected Service Account token to Vault, and Vault verifies it against the Kubernetes API to issue a Vault token.

Q3: What is the difference between a Deployment and a StatefulSet?Answer:Deployment: Managed for stateless applications (e.g., web APIs). Pods are interchangeable, use random string names, and can be destroyed or recreated instantly without data loss because data is stored externally.StatefulSet: Managed for stateful applications (e.g., databases, or a HashiCorp Vault cluster). Pods have a persistent, predictable identifier (e.g., vault-0, vault-1) and stick to their specific dedicated storage volumes even if restarted.

Q4: What are the two types of probes used to monitor Pod health?Answer:Liveness Probe: Checks if the container is still running. If it fails, Kubernetes kills the container and restarts it.Readiness Probe: Checks if the container is ready to accept network traffic. If it fails, Kubernetes removes the Pod from the Service load balancer so users don't hit a broken page.Tricky & Advanced Scenario Questions

Q5: "We deployed Vault using the official Helm chart in High Availability (HA) mode with 3 replicas. However, Kubernetes keeps showing 2 out of the 3 Vault Pods as NOT READY (0/1). Is the cluster broken?"Answer: No, this is normal behavior by design.In a Vault HA cluster, only one node is active (the leader) and unsealed, while the other two are standby nodes. The official Helm chart configures the Readiness Probe to fail on standby nodes so that the Kubernetes Service load balancer only routes active application traffic to the primary leader. The pods are healthy; they are just waiting in standby mode.

Q6: "You are using the Vault Agent Injector sidecar pattern. A developer complains that their application container crashes immediately on startup because it cannot find the secrets file. How do you fix this race condition?"Answer: This happens because the application container is starting up and looking for the secrets file before the Vault Agent sidecar container has finished initializing, authenticating, and rendering the secret to the shared volume.The Fix: Configure the Vault Agent annotation to run as an Init Container (://hashicorp.com: "true"). This forces Kubernetes to successfully run the Vault agent, pull the secrets, and write them to the shared volume before the main application container is ever allowed to boot up.

Q7: "If a Kubernetes Service Account token is stolen, how does Vault mitigate the security risk?"Answer: Vault mitigates this in two structural ways:Short Lifespans: Modern Kubernetes Service Account tokens (bound projected volumes) have a very short default lifespan (often 1 hour).Token Review API: When someone passes a stolen token to Vault, Vault immediately validates it in real-time against the Kubernetes API. If the token has expired, or if the specific Pod that owned it has been deleted, Kubernetes tells Vault the token is invalid, and Vault instantly rejects the login request.

Q8: "What is the difference between a ConfigMap and a Secret in Kubernetes, and why do companies use Vault anyway if Kubernetes has 'Secrets' natively?"Answer:ConfigMap vs Secret: ConfigMaps store plain-text configuration. Kubernetes Secrets store sensitive data, but by default, they are only obfuscated using Base64 encoding, which is easily decoded by anyone with access to the cluster.
Why Vault is needed: Kubernetes secrets are static, stored unencrypted in etcd (unless encryption-at-rest is manually turned on), and lack advanced security features. Vault provides true encryption, automatic rotation, dynamic secrets, fine-grained access policies, and a complete audit trail that Kubernetes secrets cannot match.
